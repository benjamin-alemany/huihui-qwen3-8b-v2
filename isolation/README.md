# Untrusted project execution — integration disabled

This is the original credential-free isolation implementation for the prepared workstation. It provisions nothing, uses no model, and does not enable OpenCode or code-server tools. Initial scope is **pure Python unittest projects**, not a general development terminal.

- `files.py`: broker-owned private disposable project, relative path validation, fd-relative no-follow access, single-link regular files, UTF-8 bounded reads, atomic compare-and-swap edits, file/project quotas, independent bounded snapshots. No shell, URL fetch, credential/config file, promotion, backup or saved-project API.
- `broker.py`: exact request schemas for `read`, `write`, and fixed `test`. A request cannot supply command, environment, mount, network destination or resource limits. No HTTP listener or harness connection.
- `prepare_runtime.py`: trusted image-build stage creates a sealed minimal Python runtime from OS Python/stdlib/shared libraries and a native seccomp filter. No shell/package manager, model files, cloud secrets, provider sockets or user home. Run as root only during image build; never on agent-controlled input. OS package provenance must be separately recorded for each image.
- `sandbox.py`: unprivileged Linux only. Mandatory user/mount/PID/network/IPC/UTS namespaces, dropped capabilities, no_new_privs through bubblewrap, nested user namespaces disabled, native syscall allowlist, root-owned read-only runtime/policy, fresh read-only project snapshot, bounded 16 MiB `/tmp`, no GPU devices, cleared environment and closed inherited descriptors. Sealed `python3 -I -B /opt/test-runner.py` entrypoint stacks a second seccomp filter denying exec before discovering project tests. Seccomp denies sockets (including local Unix sockets), DNS transport, process creation, namespace/mount changes, tracing, keyrings, BPF/perf and io_uring. CPU/address-space/file-size/fd/process/core limits plus wall-time/output bounds. Errors never fall back to host execution.
- `verify.py`: trusted adversarial tests for real namespaces, capability/no_new_privs/seccomp status, socket/DNS denial, hidden host paths, credential stripping, read-only mounts, memory/process constraints, wall/output bounds, and a normal broken-test/edit/fixed-test cycle. Dummy data only. Reports a result for **this host**, never automatically authorizes agent tools or certifies Runpod.

Free checks: `python3 -B -m unittest discover -s isolation/tests -v`.

Linux OS verification requires the pinned bubblewrap build, libseccomp and the sealed runtime. See the **manual-only** `isolation-cpu.yml` workflow: public repository, standard CPU runner, read-only repository token, no saved artifacts/caches, no model or cloud account calls. It does not change host AppArmor/sysctl/seccomp settings or use privileged containers. If required kernel features are unavailable the job fails closed.

The implementation is not an audited VM boundary. The same Linux kernel remains shared. Execution requires a dedicated UID so process-count limits do not collide with unrelated services. The file broker expects a private broker-owned directory that is not concurrently writable by the model/harness or a direct editor. Do not run a multithreaded service around `preexec_fn`; the execution component currently requires a single-threaded process. No cgroup integration is claimed; the single-process syscall policy and rlimits constrain this initial scope. Extending the language/runtime/syscall set requires renewed review and adversarial verification.

Production gates remain outside these modules: deny-all OpenCode config, disabled benchmark runner, no Pod launch from the controller. Before enabling any tools, verify on the actual Runpod host/image, attest the image/broker/policy/runtime identity, implement the trusted harness bridge with no direct-tool bypass, isolate the harness itself from host network/files and enforce the editor/terminal boundary. Persistent project promotion and separate encrypted backups must remain outside executable scratch. No control keys may enter the Pod. Successful CPU verification does not prove model safety or reliable tool use.
