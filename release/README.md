# Chat release record

`manifest.json` is the shared model, artifact, hosting and duration record.
It is a pinned `candidate`, not an accepted production release. The serving image,
bootstrap package lock, bundle digest, compressed size, source commit and runtime
orchestrator are pinned. The exact image passed free published-artifact checks
for copied code, offline cache and runtime imports; native acceptance is pending.
The one-allocation acceptance stopped at provider reservation identity readback,
before model permission. The source acceptance pin is limited to the exact separately owner-approved candidate; production approval remains closed. No native
CUDA/model result is established by that attempt. Account catalog IDs and
passing CPU tests do not prove driver, toolkit, container or model compatibility.

Use the reviewed GitHub branch for code. Keep account environment/key names,
provider keys, Cloudflare connector secrets, existing resource/data identities,
owner identity and financial ledgers in the separate private deployment overlay.
The old private source tree is not a second deployment source. Staging must copy
both `cloudflare-backup/` and `release/` so their relative imports retain meaning.

The controller loads the reviewed bundle and renderer from canonical source.
The host downloads that bundle from the fixed public GitHub commit/path and
checks its pinned size and hash before installation. This does not authorize a VM.

A pinned candidate is only preparation for a separately approved, one-allocation
acceptance. It must not unlock ordinary sessions. Production promotion requires
the exact accepted image/bootstrap/host profile and native/browser/cleanup
receipts. Ordinary allowance starts at zero, independently of the test ledger.

No environment variable, owner browser input, inference output or passing CPU
check may substitute for native release acceptance. All new provider execution
remains explicitly selected; uncertain legacy resources must be reconciled before
migration rather than silently reassigned to another provider client.

Local V2 preparation pins `hosting.ownershipPolicy: nonce-name-v2` in the release,
source approval and quote consent binding. New reservations carry that explicit
version and bind the full random nonce-bearing name, target and creation window;
provider labels remain truthful diagnostic data. Absent ownership policy retains
the old label-based V1 predicate. The failed V1 attempt and its operator cleanup
record are historical evidence, not V2 reservations or permission to retry.

The ownership-only repair left VM/bootstrap/serving artifacts unchanged.
The subsequent bounded host-progress preparation refreshes the root-host bundle
for diagnostics; it leaves the serving image, model and isolation policy unchanged. Production approval remains closed; the source acceptance pin alone does not authorize a create. V2 has only
local CPU/dummy coverage until separately approved native acceptance succeeds.
